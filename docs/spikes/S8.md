## 2. Interfaces(정본 산출, MASTER 인터페이스 확장)

```ts
type EffectState = "intended" | "committed" | "failed" | "unverifiable";
type Decision    = "done" | "reapply_with_approval" | "conflict" | "unverifiable";
type EffectSpec  =
  | { kind: "file_patch"; path; baseBlob; targetBlob; patchHash; fileMode }
  | { kind: "git_commit"; parentSha; treeSha?; message }
  | { kind: "net" | "mcp" | "external_service"; target; externalRef: string | null };

class EffectLedger {
  constructor(file);  static load(file)
  get(key): EffectEntry | undefined          // { key, spec, state, intendedAt, committedAt, result(outbox), assessments[] }
  intend(key, spec)                          // PK 거부: duplicate idempotency key
  recordResult(key, result)                  // commit 전 중간 산출(생성 SHA 등) — outbox
  commit(key) / fail(key, reason)
  assess(key, currentBlob): Decision                       // file_patch 3분기 (done 이면 committed 로 전이)
  assessGitCommit(key, { headSha, shaExists }): Decision   // SHA 존재 → done(재커밋 금지) / parent=HEAD → reapply / 그 외 conflict
  assessExternal(key, verify?): Decision                   // external_ref·검증기 없으면 unverifiable
}
function blobOf(data: Buffer): string       // git blob sha1
```

MASTER의 `EffectLedger { intend(key,{path,baseBlob,targetBlob,patchHash}); commit; assess }`에 (1) `kind` 판별자, (2) git_commit·external 전용 assess, (3) outbox `recordResult`, (4) `fileMode`(DATABASE_SCHEMA §3 file_patch 필드)를 더했다. 이유: Step 1 단언 "git commit outbox에 SHA가 있으면 재커밋하지 않음"과 RC-S13 `unverifiable`은 file_patch 전용 `assess` 하나로 표현할 수 없다(ledger Ruling).

## 3. 설계 메모 (P04 T3·T4 / P05 입력)

- **원칙**: 원장은 효과를 적용하지 않는다. `assess*`는 판정과 원장 상태 전이만 하고, 재적용은 호출자가 **승인을 받은 뒤** 한다. `done`만 자동 전이(현재 상태가 이미 목표와 일치하므로 안전). `reapply_with_approval`·`conflict`·`unverifiable`은 원장 상태를 바꾸지 않는다(`unverifiable`만 상태를 `unverifiable`로 표시해 자동 재시도 경로에서 제외).
- **쓰기 순서**(outbox): `intend` → (효과 실행) → `recordResult`(생성 SHA) → `commit`. 어느 지점에서 죽어도 재기동 판정이 결정적이다: intend 전 죽음 = 효과 없음·원장 없음, intend 후 = 현재 상태 대조, SHA 기록 후 = 존재 확인. git_commit은 `git commit` 자체가 SHA를 돌려주므로 "커밋은 됐는데 SHA 기록 전 죽음"이 남는다 → parent=HEAD 검사로는 `conflict`(HEAD가 새 커밋으로 이동)가 나와 **보류**된다. 자동 재커밋이 아니라 보류이므로 안전하지만, 사람이 대조해야 한다(§5 한계 1).
- **file_patch의 `patch_hash`·`file_mode`**는 기록만 한다. 판정은 blob 비교로 충분하고(DATABASE_SCHEMA §3 "현재 blob=target→done…"), patch_hash는 P04에서 같은 target blob을 다른 패치가 만든 경우를 구분하는 감사 필드로 쓴다.
- **DATABASE_SCHEMA 대응**: `effects.idempotency_key` PK ↔ `intend` 거부, `kind`/`state`/`payload`(spec)/`result`(outbox)/`committed_at` ↔ `EffectEntry`. SQLite 전환 시 `persist()`를 트랜잭션 UPSERT로 바꾸면 된다(스파이크는 파일 JSON + tmp/rename).
- **크래시 재현 방법**: `spawnSync(process.execPath, ["--import","tsx", worker, …])`(S5·S7과 같은 자식 TS 실행 패턴) + worker 안 `process.kill(process.pid, "SIGKILL")`. Windows에서는 `TerminateProcess`로 `status 1, signal null`, Linux는 `status null, signal "SIGKILL"` — 테스트는 `status !== 0`만 단언해 양쪽 CI에서 같은 의미를 갖는다. 정상 종료 경로는 없다(`setTimeout(exit 99)` + throw로 봉쇄).

## 5. 한계

1. **"커밋됐는데 SHA 기록 전 크래시"**는 `conflict`로 보류된다(자동 재커밋 없음 — 안전 측). 메시지·tree 비교로 "내 커밋"을 식별하는 보완은 P04 T4에서 `treeSha`를 intend 시점에 기록해(`git write-tree`) HEAD의 tree·parent와 대조하면 된다. 스파이크는 `treeSha`를 선택 필드로만 둔다.
2. **fsync 없음**: tmp+rename은 프로세스 크래시에는 원자적이지만 전원 차단은 다루지 않는다. SQLite WAL(P01 T7)로 넘어가면 해결된다.
3. **원장 파일 1개·단일 프로세스 가정**: 동시 writer 잠금 없음. 데몬이 단일 writer(SYSTEM_ARCHITECTURE §4)이므로 제품에서는 문제가 안 되지만, 스파이크 원장을 여러 프로세스가 동시에 열면 마지막 쓰기가 이긴다.
4. **`assessExternal`의 검증기는 호출자 주입**: 실제 외부 서비스(MCP·HTTP) 대조는 P05 TEST-RC-S13 E2E 범위. 여기서는 "참조 없으면 unverifiable, 자동 전이 없음"만 증명했다.
5. `assess`는 `committed` 상태면 blob과 무관하게 `done`을 돌려준다(이미 완료된 효과를 다시 묻는 경우). 완료 후 사용자가 파일을 되돌린 경우를 "재적용 필요"로 보지 않는 것은 의도(효과는 1회 완료됐고, 이후 변경은 새 효과)지만, P04에서 "완료 후 되돌림 감지"를 원하면 별도 비교가 필요하다.
