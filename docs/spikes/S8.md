## 2. Interfaces(정본 산출, MASTER 인터페이스 확장)

```ts
type EffectState = "intended" | "committed" | "failed" | "unverifiable";
type Decision    = "done" | "reapply_with_approval" | "conflict" | "unverifiable";
type EffectSpec  =
  | { kind: "file_patch"; path; baseBlob; targetBlob; patchHash; fileMode }
  | { kind: "git_commit"; parentSha; treeSha; message }                 // parent·tree 필수(리뷰 #3)
  | { kind: "net" | "mcp" | "external_service"; target; externalRef: string | null };
interface GitInspector { headSha: string; inspect(sha): { parents: string[]; tree: string } | null }

class EffectLedger {
  constructor(file);  static load(file)
  get(key): EffectEntry | undefined          // { key, spec, state, intendedAt, committedAt, result(outbox), assessments[] }
  intend(key, spec)                          // PK 거부: duplicate idempotency key
  recordResult(key, result)                  // commit 전 중간 산출(생성 SHA 등) — outbox
  commit(key)                                // unverifiable 이면 예외(리뷰 #1)
  fail(key, reason)
  assess(key, currentBlob): Decision                 // file_patch 3분기 (done 이면 committed 로 전이)
  assessGitCommit(key, repo: GitInspector): Decision // 기록 SHA 존재+parent·tree 일치 → done / HEAD 가 intent 와 일치 → done+SHA 복구 / parent=HEAD → reapply / 그 외 conflict
  assessExternal(key, verify?): Decision             // external_ref·검증기 없으면 unverifiable; 이미 unverifiable 이면 재평가 없음
  resolveUnverifiable(key, { outcome: "done"|"failed", by, note? })  // 사용자 대조 — unverifiable 의 유일한 탈출
}
function blobOf(data: Buffer): string       // git blob sha1
```

MASTER의 `EffectLedger { intend(key,{path,baseBlob,targetBlob,patchHash}); commit; assess }`에 (1) `kind` 판별자, (2) git_commit·external 전용 assess, (3) outbox `recordResult`, (4) `fileMode`·`treeSha`(DATABASE_SCHEMA §3 필드), (5) `resolveUnverifiable`를 더했다. 이유: Step 1 단언 "git commit outbox에 SHA가 있으면 재커밋하지 않음"과 RC-S13 `unverifiable`은 file_patch 전용 `assess` 하나로 표현할 수 없다(ledger Ruling). 리뷰는 이 확장이 DATABASE_SCHEMA §3·D16과 정합적이라고 봤고, 빠진 필수 입력(tree)만 지적했다.

## 3. 설계 메모 (P04 T3·T4 / P05 입력)

- **원칙**: 원장은 효과를 적용하지 않는다. `assess*`는 판정과 원장 상태 전이만 하고, 재적용은 호출자가 **승인을 받은 뒤** 한다. 자동 전이는 `done` 하나뿐이고, 그것도 현재 상태가 intent와 **정확히** 일치할 때만이다(file blob = target / 기록 SHA의 parent·tree = intent / HEAD의 parent·tree = intent). `reapply_with_approval`·`conflict`는 원장 상태를 바꾸지 않고, `unverifiable`은 상태를 `unverifiable`로 표시해 자동 재시도 경로에서 제외하며 **사람의 `resolveUnverifiable`만** 이를 바꿀 수 있다.
- **쓰기 순서**(outbox): 스테이징 → `intend(parent, tree)` → (효과 실행) → `recordResult`(생성 SHA) → `commit`. **시험한 다섯 크래시 지점**(리뷰 #6 범위 명시): intend 후 적용 전(B·C), 적용 후 commit 전(A), git commit 전(E), git commit 후 SHA 기록 전(F), SHA 기록 후 commit 전(D) — 모두 결정적 판정이 나왔다. intend·recordResult의 **쓰기 도중**(rename 직전) 크래시는 주입하지 않았다(§5 2).
- **"내 커밋" 식별**: intent의 `treeSha`(`git write-tree`)와 `parentSha`로 기록 SHA 또는 HEAD를 대조한다. 같은 tree·parent라면 메시지가 달라도 내용은 같은 커밋이므로 `done`으로 본다(복구 시 `result.sha`를 HEAD로 채우고 `recoveredBy: tree_match` 기록). 1차의 "SHA 기록 전 크래시 → conflict 보류" 한계는 이것으로 해소됐다.
- **file_patch의 `patch_hash`·`file_mode`**는 기록만 한다. 판정은 blob 비교로 충분하고(DATABASE_SCHEMA §3), patch_hash는 P04에서 같은 target blob을 다른 패치가 만든 경우를 구분하는 감사 필드로 쓴다.
- **DATABASE_SCHEMA 대응**: `effects.idempotency_key` PK ↔ `intend` 거부, `kind`/`state`/`payload`(spec)/`result`(outbox)/`committed_at` ↔ `EffectEntry`. SQLite 전환 시 `persist()`를 트랜잭션 UPSERT로 바꾸면 된다(스파이크는 파일 JSON + tmp/rename).
- **크래시 재현 방법**: `spawnSync(process.execPath, ["--import","tsx", worker, …])`(S5·S7과 같은 자식 TS 실행 패턴) + worker 안 `process.kill(process.pid, "SIGKILL")`. Windows는 `TerminateProcess`로 `status 1, signal null`, Linux는 `status null, signal "SIGKILL"` — 테스트는 `expectCrashed`로 플랫폼별 값과 `error` 부재, stdout의 크래시 표식을 단언한다(리뷰 #4). 정상 종료 경로는 없다(`setTimeout(exit 99)` + throw로 봉쇄).

## 5. 한계

1. **다른 ref·reflog 불변은 검사하지 않는다**(리뷰 #3): (D)의 증거는 현재 HEAD와 `rev-list --count`다. 재커밋이 다른 브랜치에 생기는 경로는 이 스파이크에 없지만 단언으로 배제하지도 않았다. P04 T4에서 `for-each-ref` 스냅숏 비교로 보강.
2. **쓰기 도중 크래시 미시험**(리뷰 #6): tmp+rename은 프로세스 크래시에 원자적이지만 rename 직전 크래시는 "intent 미기록 = 효과 미시도"로 떨어지는지 주입해 보지 않았다. fsync도 없어 전원 차단은 다루지 않는다. SQLite WAL(P01 T7) 전환 시 트랜잭션·writer 제어·내구성 설정으로 대체.
3. **원장 파일 1개·단일 프로세스 가정**: 동시 writer 잠금 없음. 데몬이 단일 writer(SYSTEM_ARCHITECTURE §4)이므로 제품에서는 문제가 안 되지만, 스파이크 원장을 여러 프로세스가 동시에 열면 마지막 쓰기가 이긴다.
4. **`assessExternal`의 검증기는 호출자 주입**: 실제 외부 서비스(MCP·HTTP) 대조는 P05 TEST-RC-S13 E2E 범위. 여기서는 "참조·검증기 없으면 unverifiable, 자동 전이 없음, 사용자 대조로만 해소"를 증명했다.
5. **file_patch `assess`는 `committed` 상태면 blob과 무관하게 `done`**: 완료된 효과를 다시 묻는 경우이며, 완료 후 사용자가 파일을 되돌린 것은 새 변경으로 본다(의도 — git_commit과 달리 blob은 "소실"이 아니라 "이후 편집"이기 때문). P04에서 "완료 후 되돌림 감지"를 원하면 별도 비교가 필요하다. git_commit은 리뷰 #2에 따라 `committed`라도 SHA 존재·일치를 다시 확인한다.
6. **mtime 불변은 쓰기 0회의 엄밀한 증명이 아니다**(리뷰 #7): 파일시스템 시간 해상도 한계. (A)의 핵심 증거는 blob=target + `assess`가 파일 API를 호출하지 않는 코드 구조이며, 실제 복구 실행기의 재실행 0회는 E2E에서 확인한다.
