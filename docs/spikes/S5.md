## 2. Interfaces(정본 산출)

```ts
// launcher.ts
interface DaemonHandle { pid: number; startedAt: string; nonce: string; port: number; tokenRef: string; assessment?: LockAssessment; spawned: boolean }
interface LockFile { pid: number; startedAt: string /* OS 프로세스 생성 시각(CIM CreationDate, UTC ISO) */; nonce: string; port: number; protocolVersion: number }
type LockAssessment = { verdict: "live" } | { verdict: "connectable" } | { verdict: "stale"; reason: "pid_gone" | "pid_reused" | "nonce_mismatch" | "bad_timestamp" }
type ConnectErrorKind = { kind: "incompatible" | "unauthorized" | "forged" | "unreachable"; code: number | null }
assessLock(lock, { pidAlive, processStartedAt, helloNonce }) → LockAssessment   // 순수
classifyConnectError(err) → ConnectErrorKind                                   // 순수
// protocol.ts
proof(token, serverNonce, clientNonce, role: "server" | "client") → hex(HMAC-SHA256)
```

- **핸드셰이크(토큰 미전송, 리뷰 #1)**: `hello{clientNonce, protocolVersion}` → `challenge{serverNonce, nonce, pid, serverProof=HMAC(token,"server|serverNonce|clientNonce")}` → 클라이언트가 serverProof·pid·nonce를 락과 대조(실패 시 **즉시 중단**) → `auth{clientProof=HMAC(token,"client|…")}` → `welcome{seq,pid,nonce,protocolVersion}`. 거부: `4001`(형식·증명 불일치) / `4002`(hello 3초 타임아웃) / `4003`(프로토콜 불일치). 비교는 `timingSafeEqual`.
- **startedAt의 출처**: 데몬이 기동 시 자기 pid의 CIM `CreationDate`를 락에 쓰고, launcher도 같은 CIM 출처로 대조한다(스크립트 시작 시각이 아님). 같은 출처라 정상이면 문자열이 같고, **허용 오차 2초**는 직렬화·시계 반올림 여유다(PID 재사용은 분 단위 이상 차이). 날짜가 아니면 `bad_timestamp`로 stale(리뷰 #8).
- **ensureDaemon 분기(리뷰 #3)**: `live` → 재접속 / `stale`(pid_gone·pid_reused·nonce_mismatch·bad_timestamp) → 락 삭제 후 spawn / 접속 오류 `incompatible`(4003)·`unauthorized`(4001)·`forged`(증명 실패) → **락 보존 + 명시적 오류**(새 데몬 금지) / `unreachable`(TCP 오류·1006) → 500ms 간격 3회 재시도 후 락 보존 + 오류.
- **spawn 배타 락(리뷰 #2)**: `spawn.lock`을 `O_EXCL`로 만든 launcher만 데몬을 띄우고, 나머지는 `daemon.lock`이 나타나길(20초) 기다려 접속한다. 60초 넘은 `spawn.lock`은 stale로 제거. 완료 후 삭제.
- **토큰**: launcher가 기동 전 `<stateDir>/token`(24바이트 hex)을 쓰고 데몬이 읽는다. `tokenRef`는 이 파일 경로(제품: 키링 항목 id, SECURITY §7). 토큰은 네트워크로 전송되지 않는다.
- **락 파일 원자성**: `daemon.lock.tmp` → `rename`. shutdown 시 삭제.
- **WS**: `ws` 8(서버), 클라이언트는 Node 24 전역 `WebSocket`. 메시지: 핸드셰이크 4종, `status`, `spawnChildren{count,withGrandchild}`, `shutdown`, 서버 푸시 `event{seq}`.

## 3. 실측 메모

- **부모 종료 후 생존**: `detached:true + stdio:'ignore' + unref()`만으로 부모(launcher) `process.exit(0)` 뒤에도 데몬이 남았다(`daemonProcess.ppid`가 목록에 없음). vitest 워커 안에서 띄우지 않고 **별도 launcher 프로세스**를 써서 "부모 프로세스 종료"를 실제로 만들었다(두 번째 launcher도 별도 프로세스).
- **위조 락 방어의 한계**: 락 파일을 쓸 수 있는 로컬 프로세스는 포트를 바꿔 launcher를 자기 서버로 유도할 수 있다. HMAC 상호 인증으로 **토큰·클라이언트 증명은 유출되지 않지만**, 공격자는 `hello`를 받을 수 있고 정상 데몬 접속을 막을 수 있다(DoS). 제품은 키링 토큰 + 사용자 전용 디렉터리 ACL(`%LOCALAPPDATA%`)로 락 접근을 통제해야 하며, 이 스파이크는 그 전제를 입증하지 않는다.
- **동시 기동**: `spawn.lock`(O_EXCL) 없이 두 launcher가 동시에 돌면 둘 다 `daemon.lock`을 지우고 데몬을 띄울 수 있었다(리뷰 #2 지적, 3차에서 배타 락 추가 후 실측 1개).
- **프로세스 트리 정리**: 데몬이 `child.pid`마다 `taskkill /T /F /PID`를 호출 → 자식·손자·각 콘솔 호스트까지 종료. 데몬 자신은 응답 전송 200ms 뒤 `process.exit(0)`; 이때 tsx의 `esbuild.exe` 서비스 자식(스파이크 런타임 부산물, 제품 데몬에는 없음)도 함께 사라졌다. **Job Object가 필요해지는 조건**(이 실험 밖): 자손이 `detached`/breakaway로 부모 관계를 끊는 경우, 데몬이 **비정상 종료**(크래시·강제 kill)해 shutdown 핸들러가 돌지 않는 경우 — 후자는 TEST-RC-02 범위이며 자손이 고아가 된다. P11a에서 "데몬 크래시 시 자손 정리"가 요구되면 Job Object(네이티브 헬퍼) 결정(R16 유지).
- **taskkill 출력 로캘**: 메시지가 OS 로캘(cp949)이라 본문 대신 `PID <n>` 토큰만 추출해 기록(1차 픽스처는 깨진 문자였음).
- **conhost.exe**: `windowsHide:true`로 띄운 자식 `node.exe`마다 `conhost.exe`가 붙는다(숨김 콘솔). 데몬 자체에는 없음. "창이 보이지 않는다"는 화면 관찰이 필요해 사용자 확인 항목으로 남긴다.
- **seq**: 250ms 간격 증가, welcome에 현재 seq 포함, 구독자에게 `event{seq}` 푸시. 한 연결 안에서는 누락 없음을 단언했고, 재접속 간 "연속"은 **역행 없음**만 단언한다(이벤트 복구 `subscribe(fromSeq)`는 P01 Journal).
- **정리 안전성(리뷰 #6)**: 테스트는 기동 직후 `{pid, startedAt}`을 보관하고 `afterAll`에서 CIM으로 **같은 생성 시각인 경우에만** `taskkill`한다(PID 재사용된 다른 프로세스를 죽이지 않음).
- **CIM 조회 비용**: `Get-CimInstance Win32_Process` 전체 목록 + `ConvertTo-Json` 약 0.5~1초/회. 제품 launcher는 단일 pid 필터 쿼리로 줄인다.

## 4. 재부팅 stale 락 — 수동 절차(RC-03 모의, P05에서 실제 1회)

1. 데몬 기동 후 `daemon.lock`의 `pid`·`startedAt`을 기록한다.
2. 재부팅(또는 모의: 데몬을 `taskkill /F`로 죽이고, 같은 pid가 다른 프로세스에 재사용된 상황을 `startedAt`을 바꿔 만든다).
3. launcher `ensureDaemon` 실행 → `probeProcess(pid)`: (a) pid 없음 → `stale/pid_gone`, (b) pid는 있으나 CIM 생성 시각이 락과 2초 넘게 다름 → `stale/pid_reused`, (c) 락의 시각이 날짜가 아님 → `stale/bad_timestamp`, (d) 같은 pid·시각이지만 nonce 불일치 → `stale/nonce_mismatch`.
4. stale이면 락 삭제 → 새 데몬 spawn → `assessment`에 stale 사유가 남는다(RecoveryManager 입력: "재부팅 후 복원" 판정 근거). **접속 오류(incompatible/unauthorized/forged/unreachable)는 stale이 아니므로 락을 지우지 않고 오류로 끝난다.**
5. 부트 ID 변경 감지는 이 스파이크에서 다루지 않았다(P05 REC-05: `startedAt` 대조가 PID 재사용을 덮으므로 부트 ID는 보조 신호).
